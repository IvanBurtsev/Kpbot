# kpbot — «заявка из письма → коммерческое предложение»

Прототип сервиса для оптовиков и производств: письмо с заявкой превращается в готовое КП
и черновик ответа, который отправляет человек.

```
письмо .eml → позиции → матчинг с прайсом → расчёт (цена/НДС/доставка) → КП (HTML/DOCX/PDF) → черновик ответа → одобрение человеком
```

## Почта

Два способа входа. Если в аккаунте Google нет «Паролей приложений» (включена защита аккаунта,
политика Workspace или вход по ключам доступа) — остаётся только OAuth.

**A. OAuth2 для Gmail (рекомендуется).**

Полностью через консоль нельзя: OAuth-клиент типа **Desktop app** создаётся только в веб-консоли
Google (gcloud такого не умеет, а IAP-клиенты — другой тип и для Gmail IMAP не подходят).
Один раз подтвердить доступ в браузере придётся в любом случае — это модель безопасности Google.

Всё остальное завернуто в мастер:

```powershell
python scripts/google_setup.py
```

Он откроет три страницы, спросит Client ID и Client secret, запишет их в `.env`,
запустит `oauth-login` и `mail-check`. Вручную то же самое:

1. console.cloud.google.com → создать проект → APIs & Services → включить **Gmail API** (для IMAP не обязательно, нужно для push-уведомлений).
2. OAuth consent screen / Google Auth Platform → Get started → **External** → Test users → добавить свой адрес.
3. Credentials → Create credentials → **OAuth client ID** → тип **Desktop app**.
4. В `.env`: `KPBOT_OAUTH_CLIENT_ID`, `KPBOT_OAUTH_CLIENT_SECRET`, `KPBOT_IMAP_USER`.
5. `python -m kpbot.cli oauth-login` → в браузере «Дополнительно → Перейти в kpbot → Разрешить».
6. `python -m kpbot.cli mail-check`

Пока приложение в статусе «Testing», верификация Google не нужна: достаточно добавить свой
аккаунт в список тестовых пользователей (до 100 человек).

**B. Пароль приложения (Yandex, Mail.ru, корпоративный IMAP).**

`KPBOT_IMAP_PASSWORD` в `.env` (16 символов из настроек почты), затем `mail-check`.

```powershell
python -m kpbot.cli mail-check          # сколько писем и непрочитанных, без изменений
python -m kpbot.cli mail-preview --limit 3 --unseen   # что бот увидит, без записи в базу
python -m kpbot.cli poll --dry-run      # только состояние ящика
python -m kpbot.cli poll --limit 5      # разобрать 5 непрочитанных и пометить прочитанными
```

`poll` читает письма через `BODY.PEEK[]` (не помечает прочитанными при просмотре) и ставит
`\Seen` только после успешной обработки. Если что-то упало — письмо останется непрочитанным.

**Письмо без позиций — не заявка.** Рассылки, уведомления и «добрый день» не создают карточку
в очереди: такие письма пропускаются, попадают в `data/out/skipped.jsonl` (uid, отправитель,
тема) и помечаются прочитанными, чтобы не разбирать их повторно. Отключается
`KPBOT_IMAP_MARK_SKIPPED=false`. Без этого правила реальный ящик с тысячей рассылок
превращается в тысячу пустых заявок.

## Производительность матчинга

Замер (`python scripts/bench.py`): 20 строк заявки, прайс разного размера.

| Позиций | Сборка индекса | 20 строк | На строку |
|---|---|---|---|
| 100 | 6 мс | 5 мс | 0,24 мс |
| 1 000 | 53 мс | 37 мс | 1,9 мс |
| 10 000 | 493 мс | 80 мс | 4,0 мс |

Индекс строится один раз на версию прайса и переиспользуется. Дальше по плану —
pg_trgm в Postgres, чтобы не держать весь прайс в памяти процесса.

## Чего нет (сознательно)

- реального IMAP/SMTP: нужны доступы (Gmail — OAuth или пароль приложения), это следующий шаг;
- LLM-извлечения: интерфейс `LineExtractor` готов, правило-экстрактор детерминированный;
- интеграции с 1С и мультитенантности;
- биллинга и регистрации;
- PDF в этом окружении: headless Edge/Chrome здесь падают (песочница), поэтому основной
  формат — HTML (печать в PDF из браузера) и DOCX. На обычном сервере PDF включается сам:
  адаптер пробует Chrome, затем Edge, и запоминает результат.

## Как это устроено

```
api/ FastAPI ──┐
               ├── pipeline.py (use case: ingest → match → price → render → draft)
worker/  нет ──┘        │
                        ├── domain.py     сущности, деньги, расчёт (без I/O)
                        ├── matching.py   нормализация и скоринг
                        ├── extract.py    извлечение позиций (правила; LLM — за интерфейсом)
                        ├── pricelist.py  XLSX/CSV
                        ├── mailparse.py  .eml и сборка ответа
                        ├── render.py     Jinja2 → HTML, python-docx → DOCX, браузер → PDF
                        └── store.py      SQLite: заявки, строки, КП, артефакты, журнал
```

Полная версия решений и чек-лист безопасности — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Безопасность (что уже сделано)

- **SQL-инъекции:** только параметризованные запросы (`?`), ни одной склейки строк.
- **Валидация:** Pydantic с `extra="forbid"`, лимиты на размер письма, число строк, длину полей.
- **XSS:** Jinja2 autoescape, пользовательский текст не попадает в разметку сырым.
- **CSRF:** токен в каждой форме, проверяется на сервере.
- **Доступ:** интерфейс — пароль + подписанная HttpOnly-cookie; API — ключ, сравнение constant-time.
- **Лимиты:** размер тела запроса проверяется до чтения, rate limit на вход и загрузку.
- **Заголовки:** CSP, `X-Frame-Options: DENY`, `nosniff`, `no-referrer`.
- **ПДн:** письма не логируются целиком, наружу (LLM) ничего не уходит — LLM выключен.
- **«Защита от дурака»:** модель не назначает цену; строки без уверенного матча не попадают
  в расчёт и уходят человеку; отправка только после одобрения; дубли писем не создают заявок.

## Качество разбора

```powershell
python -m kpbot.cli eval --verbose
```

8 размеченных писем (опечатки, пропущенные единицы, количества словами, рассылка):

| Метрика | Только правила | С LLM |
|---|---|---|
| Полнота (recall) | 83% | **100%** |
| Точность (precision) | 100% | 100% |
| Строк разобрано без человека | 76% | **82%** |
| Готовы к отправке без правок | 3 из 7 | **5 из 7** |
| «Заявка / не заявка» | 8 из 8 | 8 из 8 |

LLM закрывает то, что правилами не лечится: «полторы упаковки», «десяток», «метров двадцать».
Правила при этом не выбрасываются — они работают как страховка и как второй экстрактор,
который дополняет ответ модели, если она что-то пропустила.

Набор лежит в `kpbot/evalcases.py` — это регрессионный тест качества: любое изменение
правил или промпта, ухудшившее цифры, видно сразу.

## LLM: границы доверия

- модель **извлекает** название, количество и единицу; цены, артикулы и суммы считает только код по прайсу;
- письмо передаётся как данные, в обёртке `<<<ПИСЬМО>>>…<<<КОНЕЦ ПИСЬМА>>>`, с прямым запретом
  исполнять инструкции из текста (OWASP LLM01, prompt injection);
- ответ валидируется pydantic-схемой (`extra="forbid"`), при любом расхождении — откат на правила;
- при сбое, таймауте, 429 или невалидном JSON письмо всё равно разбирается правилами;
- ключ живёт только в `.env` (в `.gitignore`), в логи не попадает — форматтер вычищает
  `sk-…` и `GOCSPX-…`; `mail-status` показывает лишь последние 4 символа.

Включение: `KPBOT_LLM_ENABLED=true` + `KPBOT_LLM_BASE_URL`, `KPBOT_LLM_MODEL`, `KPBOT_LLM_API_KEY`.
Провайдер — любой OpenAI-совместимый (`/chat/completions`, `response_format: json_object`).
