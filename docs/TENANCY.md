# Мультитенантность: что гарантировано и как это проверено

Документ для владельца сервиса и для того, кто будет добавлять клиентов. Отвечает
на один вопрос: **могут ли два клиента пересечься**. Короткий ответ — нет, и ниже
перечислено, чем именно это обеспечено и каким тестом проверяется.

Проверка: `python -m unittest discover -s tests -p "test_isolation.py"` — набор
«красной команды», каждый тест пытается перейти границу и обязан получить отказ.

---

## 1. Модель

```
реестр (tenants.sqlite3)          база клиента (своя на каждого)
  код клиента ──────────────────► data/clients/<код>/kpbot.sqlite3
  статус active/paused            заявки, КП, прайс, остатки, пользователи,
  ключ API (хеш)                  настройки расчёта, журнал, обучение
                                  документы: data/clients/<код>/out/
```

- **Одна база — один клиент.** Нет общих таблиц с полем `tenant_id`, поэтому
  ошибка в фильтре не может показать чужие строки: их просто нет в этой базе.
- **Файлы — в папке клиента.** КП, выгрузки, письма в `sent/`, `skipped.jsonl`
  лежат в `data/clients/<код>/out`. Основной клиент остаётся в прежней `data/out`
  для совместимости с уже выпущенными документами.
- **Реестр** хранит код, имя, статус и хеш ключа API. База клиента без записи в
  реестре недостижима через веб.

## 2. Как запрос попадает в базу клиента

| Источник | Кто | Что даёт |
|---|---|---|
| Кука `kpbot_tenant` (подписана HMAC) | сотрудники поставщика в `/ui` | код клиента; сверяется с реестром на каждом запросе |
| Кука `kpbot_client_tenant` (подписана) | покупатель в `/cabinet` | поставщик, в чей кабинет он вошёл |
| Заголовок `X-Tenant` + `X-Api-Key` | интеграции | клиент, **только если ключ выдан этому клиенту** |
| Ничего из перечисленного | — | основная база (владелец сервиса) |

Куки подписываются секретом сессии: подделать код клиента нельзя, можно только
получить отказ.

## 3. Что закрыто и каким тестом

| Гарантия | Как обеспечено | Тест |
|---|---|---|
| Ключ клиента открывает только своего клиента | `registry.verify_key(tenant_id, key)` | `ApiIsolationTest::test_client_key_opens_only_own_tenant` |
| Ключ владельца **не** открывает чужие базы | общий ключ адресует только основную базу | `test_owner_key_does_not_reach_clients` |
| `X-Tenant` с неподходящим ключом не уезжает молча в основную базу | `api_auth` отвечает 401 | `test_owner_key_does_not_reach_clients` |
| Документы клиента не открываются по чужому контексту | файлы в папке клиента + проверка заявки по базе клиента | `FileIsolationTest` |
| Индекс прайса не переиспользуется между клиентами | кэш по пути базы, LRU 8 | `PriceIndexIsolationTest` |
| Сессия сотрудника не действует в базе другого клиента | в сессии записан клиент: `клиент:пользователь` | `SessionIsolationTest::test_session_of_one_tenant_does_not_work_in_another` |
| Сессия покупателя не действует в чужом кабинете | то же для куки кабинета | `test_client_cabinet_session_does_not_cross` |
| Заявки и статистика не смешиваются | разные базы | `DataSeparationTest` |
| Пропавшая база клиента не подменяется основной | middleware: кука есть, базы нет → отказ и сброс куки | `LoginWithStaleCookieTest` (вход при этом работает) |

## 4. Что НЕ изолировано (сознательно, вне кода)

Эти вещи общие на сервис и должны учитываться в договоре с клиентом:

| Что | Почему так | Что делать |
|---|---|---|
| Консоль `/ui` | это пульт владельца сервиса; владелец видит всех клиентов | клиентам — только кабинет `/cabinet`; пароль владельца не передавать |
| SMTP, Telegram, MAX | настройки сервиса, не клиента | если клиент требует свой канал — отдельное развёртывание |
| 1С (адрес, пользователь) | одна интеграция на сервис | у клиента своя база 1С — отдельный инстанс или профиль |
| LLM (ключ, модель, расход) | общий бюджет и лог расходов | считать расход по заявкам (`costs`) |
| Резервные копии | общий каталог бэкапов | шифровать, хранить в РФ (152-ФЗ) |
| Ограничитель частоты | в памяти процесса, на всех | при нескольких воркерах — Redis |

## 5. Как добавить клиента (чек-лист)

1. `/ui/ops` → «Создать клиента»: имя, код, папка базы.
2. Выдать ключ API (`/ui/ops` → «Ключ») — он показывается один раз, хранится хешем.
3. Зайти в клиента («Переключиться»), заполнить: реквизиты, **ставку НДС и режим
   цен**, прайс, почту клиента (`mail-setup --tenant <код>`).
4. Проверить: `/healthz`, затем письмо на ящик клиента и `poll --all-tenants`.
5. Проверить изоляцию: `python -m unittest discover -s tests -p "test_isolation.py"`.

## 6. Если что-то пошло не так

- **Клиент не входит** — проверьте статус в реестре (active/paused) и что файл
  базы на месте: при отсутствии базы запросы клиента отклоняются, а не уходят в
  основную базу.
- **Сменили путь базы клиента** — старые ссылки и куки перестанут работать;
  выпустите новую ссылку из `/ui/ops`.
- **Сомневаетесь в утечке** — в журнале каждого клиента есть записи
  `tenant_switch` и `login_*`; доступ к чужой базе в них не появится, потому что
  его нельзя получить.
