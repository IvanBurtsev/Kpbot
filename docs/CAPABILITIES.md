# Что продукт умеет сейчас и как его тестировать

Документ для быстрой проверки: что работает, как убедиться самому, чего нет.

## Одной фразой

Письмо с заявкой → позиции → сопоставление с прайсом → расчёт с НДС → КП (PDF/DOCX/HTML) → уведомление менеджеру → правка и отправка человеком.

## Как проверить за 10 минут

1. Открыть интерфейс (адрес и пароль — у владельца, в репозиторий не попадают).
2. Отправить на рабочую почту письмо: тема «Заявка», текст `200 шт уголок 50х50 и 50 м кабеля 3х2.5`.
3. Подождать до 10 минут (cron) — или попросить владельца запустить опрос вручную.
4. Открыть заявку: сверху видно «Разбор и КП: X с», ниже — строки, суммы и откуда взялась каждая цена.
5. Нажать «КП (PDF)», «КП (DOCX)», «Выгрузить в Excel».
6. Поправить любую строку (заменить позицию или количество) — сумма и документы пересоберутся.
7. Проверить Telegram и MAX: должно прийти уведомление со ссылкой на эту заявку.

## Роли

- **admin** — видит и правит всё, назначает исполнителей, заводит пользователей.
- **manager** — видит свободные заявки и свои, «берёт себе», правит только их.
- Пароли хранятся как PBKDF2-SHA256 с солью, сессия подписана идентификатором пользователя.
- Первый запуск создаёт администратора `admin@local` с паролем из `KPBOT_UI_PASSWORD`.

```bash
python -m kpbot.cli users                                    # список
python -m kpbot.cli user-add --email m@firma.ru --role manager --name "Иван"
```

## Приёмка заказа в 1С

Реализовано на уровне файла, без обработки на стороне 1С:

1. В карточке заявки — кнопка **«Выгрузить в Excel»**: лист «Расчёт» для человека, лист **«Для 1С»** с колонками `Код / Наименование / Количество / Цена / Сумма / Склад / Ставка НДС`.
2. В 1С: **Файл → Открыть → лист «Для 1С» → Загрузка данных из табличного документа** (стандартная обработка), сопоставление по реквизиту «Код» = артикул.
3. Дальше заказ ведётся уже в 1С как обычно.

Если обработка клиента не знает колонок «Склад» и «Ставка НДС» — удалите две последние,
остальные пять колонок прежние. `check_1c_sheet` заодно ловит повтор артикула: 1С
сопоставила бы такой код неоднозначно.

Чего в этом варианте нет: автоматической записи в 1С напрямую (обработка/HTTP-сервис) и статусов заказа обратно в kpbot.

## Остатки из 1С

```bash
python -m kpbot.cli 1c-stock                  # auto: регистр, при отказе — документы
python -m kpbot.cli 1c-stock --source documents   # приход − расход по документам
python -m kpbot.cli 1c-stock --source register    # только регистр «Товары на складах»
```

`auto` сначала читает регистр. Если он не опубликован (частый случай в облачных базах),
считает остаток как «поступления − реализации» по документам, артикул берёт из справочника
номенклатуры по ссылке. Результат кладётся в базу: страницы заявок читают остатки оттуда,
1С на каждый просмотр не опрашивается. Обновление — по cron, раз в 10–15 минут.

Записать заказ в 1С напрямую (если конфигурация это позволяет):

```bash
python -m kpbot.cli 1c-order --rfq <id> [--counterparty <Ref_Key>]
python -m kpbot.cli 1c-invoice --rfq <id> --counterparty <Ref_Key>
```

`1c-invoice` создаёт «Счёт на оплату покупателю» и подставляет организацию, склад и валюту
из справочников. Проверено на живой Бухгалтерии: **шапка создаётся, а строки с количеством
1С Fresh отбивает внутренней ошибкой OData**. Поэтому для записи счёта с позициями есть
**HTTP-сервис 1С** — он обходит это ограничение, потому что документ пишет сама 1С:

```bash
python -m kpbot.cli 1c-invoice --rfq <id> --counterparty <Ref_Key> --via service
```

Готовый код сервиса: [deploy/1c/kpbot-invoice.bsl](../deploy/1c/kpbot-invoice.bsl),
контракт и установка: [docs/ONE_C_HTTP_SERVICE.md](ONE_C_HTTP_SERVICE.md). Без сервиса
рабочий путь — файл «Для 1С». `1c-order` в Бухгалтерии честно ответит, что «Заказа
клиента» в ней нет.

## Личный кабинет клиента

```bash
python -m kpbot.cli cabinet-demo     # демо-компания и два пользователя
# → http://127.0.0.1:8000/cabinet/login
```

Покупатель видит каталог с персональной ценой, кратностью и остатком, собирает
корзину и отправляет заявку. Она падает в очередь поставщика как RFQ с готовым
расчётом — менеджер подтверждает её как обычно. Клиентов создаёт поставщик:
**Админка → Клиенты ЛК**, там же блокировка компании и добавление пользователей.
Финансы (баланс, лимит, долг, акт сверки) видит только `client_admin`.

Для 1С в ЛК есть API-заглушки: остатки, цены, статусы заказов и взаиморасчёты
(`X-API-Key`). Контракт — в [docs/CABINET.md](CABINET.md).

## Проверка после деплоя

```bash
python scripts/smoke.py --url http://127.0.0.1:8100 --api-key ... --password ...
```

Проверяет healthz, API, вход, закрытость интерфейса и статику; ничего не создаёт.
Вёрстку (если есть браузер) проверяет `scripts/e2e_browser.py`, полный HTTP-сценарий —
`tests/test_e2e_flow.py`.

## Цены из 1С

```bash
python -m kpbot.cli 1c-price            # показать, что есть в 1С
python -m kpbot.cli 1c-price --apply    # записать в прайс
```

Читается регистр «Цены номенклатуры», берётся последняя запись по каждой позиции.
Названия и единицы из уже загруженного прайса сохраняются, позиции, которых нет в 1С,
не удаляются. На тестовой базе регистр есть, но пуст — поэтому прайс там грузится файлом;
на рабочей базе клиента цены подтянутся без Excel.

Повторная выгрузка счёта не создаёт дубль: kpbot помнит номер документа в журнале решений,
`--force` — если действительно нужен второй.

## Почта по клиентам

У каждого клиента свой ящик; настройки лежат в его базе, а не в общем `.env`:

```bash
python -m kpbot.cli mail-setup --tenant <код> --host imap.yandex.ru --user zakaz@firma.ru
python -m kpbot.cli poll --all-tenants
```

`mail-setup` спрашивает пароль приложения скрыто, шифрует его ключом из `.env`
(`KPBOT_SECRET_KEY`, иначе `KPBOT_SESSION_SECRET`) и проверяет связь. Без ключа из `.env`
пароль из базы не читается — это защита от утечки копии базы.

Клиенту можно дать свой OAuth-клиент вместо пароля:

```bash
python -m kpbot.cli mail-setup --tenant <код> --host imap.gmail.com --user zakaz@firma.ru \
    --oauth-client-id ...apps.googleusercontent.com --oauth-client-secret ...
python -m kpbot.cli oauth-login --tenant <код>
```

Токен ляжет рядом с базой клиента (`data/tenants/<код>.oauth.json`), общий токен
не перетирается.

## Как включить отправку КП

Заполнить в `.env` и перезапустить сервис:

```ini
KPBOT_SMTP_ENABLED=true
KPBOT_SMTP_HOST=smtp.yandex.ru
KPBOT_SMTP_PORT=465
KPBOT_SMTP_SECURITY=ssl        # 465 → ssl, 587 → starttls
KPBOT_SMTP_USER=sales@firma.ru
KPBOT_SMTP_PASSWORD=пароль-приложения
KPBOT_SMTP_FROM=sales@firma.ru
```

Проверка без отправки: `python -m kpbot.cli smtp-check`.

Быстрая настройка (пароль спрашивается скрыто и не попадает ни в логи, ни в историю команд):

```bash
python -m kpbot.cli smtp-setup --user sales@firma.ru --host smtp.rambler.ru --port 465 --security ssl
```

## Чего нет — сознательно

- **Автоотправки без человека**: SMTP есть и проверен живой отправкой, но письмо уходит
  только после одобрения в интерфейсе.
- **Записи документов в 1С**: чтение справочников и остатков и создание номенклатуры
  работают через OData; документ поступления эта база отбивает своей ошибкой «ПередЗаписью».
- **Биллинга и регистрации**: мультитенантность есть (база на клиента, реестр, `/ui/ops`),
  денег и самостоятельной регистрации — нет.

## Что нужно сделать до первого платного клиента

1. **Прайс клиента** (100–3800 позиций) — прогнать и показать цифры на его номенклатуре.
2. **Проверка на его письмах**: 20–30 реальных заявок, замер «до/после» по времени.
3. **Договор поручения обработки ПДн** + уведомление РКН.

## Что уже меряется (для разговора с клиентом)

- время разбора письма (медиана и максимум);
- ожидание в очереди (зависит от частоты опроса почты);
- доля строк, разобранных без человека;
- стоимость разбора в рублях;
- сколько заявок и на какую сумму обработано.
