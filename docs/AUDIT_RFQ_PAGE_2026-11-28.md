# Аудит страницы заявки — 28.11.2026

**Что проверялось:** карточка заявки `/ui/rfq/{id}` — весь путь от письма до
отправленного КП: показ, разбор, правка строк, пересчёт, одобрение, отказ,
документы, отправка, права и журнал.

**Как проверялось:** чтение кода (`web.py`, `pipeline.py`, `domain.py`, `store.py`,
`render.py`, шаблон `rfq.html`), живые прогоны через `TestClient` и через поднятый
сервер (`uvicorn` на `127.0.0.1:8010`, отдельная копия данных), полный прогон
тестов.

**Итог:** 23 дефекта исправлено, добавлено 22 регрессионных теста,
**542 теста зелёные** (было 520), живой сквозной прогон и проверка вёрстки на живом Chrome.

---

## 1. Место страницы в потоке

```
письмо → разбор → матчинг → расчёт → карточка заявки → одобрение человеком
                                              ↓
                                   КП (HTML/DOCX/PDF) + черновик письма → SMTP
```

Страница — единственное место, где человек принимает решение по деньгам.
Всё, что она показывает, должно совпадать с тем, что уйдёт клиенту; всё, что
она позволяет, должно работать до конца. Поэтому «красивая» карточка, которая
расходится с письмом на копейку или показывает кнопку с заведомой ошибкой, —
это дефект, а не косметика.

## 2. Контракт страницы: что должно быть и почему

| № | Функция | Зачем | Где |
|---|---|---|---|
| 1 | Тема, отправитель, дата, статус, номер заявки | менеджер должен понимать, что за письмо и на каком оно этапе | `ui_rfq`, шапка `rfq.html` |
| 2 | Полный текст письма | проверить разбор можно только рядом с исходником | блок «Письмо клиента» |
| 3 | Разбор: строка письма, кол-во, единица, совпадение, score, остаток | видно, что сервис понял и почему | блок «Что понял сервис» |
| 4 | Статус строки: `в прайсе / похоже / не найдено / нет кол-ва` | сомнительные строки не попадают в цену молча | `LineStatus`, бейджи |
| 5 | Расчёт: строки, цена, сумма, НДС, доставка, итог | цифры должны совпадать с КП и письмом | блок «Расчёт» |
| 6 | Правка: подтвердить, заменить, кол-во, удалить, добавить | письмо «грязное», человек доводит его до КП | `lines/{idx}/*`, `lines/add` |
| 7 | Пересчёт и перерисовка КП сразу после правки | иначе менеджер отправит старый документ | `pipeline.apply_edits` |
| 8 | Одобрение человеком → черновик письма | без проверки письмо не уходит | `pipeline.approve` |
| 9 | Отказ с причиной | причина нужна в журнале и в разборе «почему не продали» | `pipeline.reject` |
| 10 | Отправка КП только после одобрения, с вложениями | «Итого» в письме и в PDF должны быть одним документом | `ui_rfq_send`, `mailer` |
| 11 | Очередь при сбое SMTP | письмо не должно теряться | `store.enqueue_message` |
| 12 | Документы: HTML, DOCX, PDF, Excel | клиенту — читаемый файл, бухгалтерии — выгрузка | `/kp.*`, `/export.xlsx` |
| 13 | Исполнитель и журнал решений | на вопрос «кто одобрил эту цену» должен быть ответ | `assign`, `decisions` |
| 14 | Права: роль, чужая заявка, CSRF, арендатор | в письмах ПДн и коммерческие условия | `ensure_rfq_id`, `verified_form` |
| 15 | Машина состояний: отправленную не правим, повторно не одобряем | иначе второе письмо и расхождение документов | `RFQ_TRANSITIONS` |

Пункты 1–15 в коде были, но часть работала не до конца. Ниже — что именно.

## 3. Найденные дефекты и исправления

### 3.1. Итоги в режиме «цены с НДС» склеивались в строку

**Было:** в карточке `172.5037.95 ₽` вместо `210,45 ₽`.
**Причина:** `quote.subtotal` и `quote.vat` — строки из SQLite; Jinja на `+`
конкатенирует строки, а не складывает числа.
**Стало:** итоги считает один код на всех (`reply_totals_rows`), карточка
получает готовые пары «подпись — сумма» и печатает их через фильтр `rub`.
**Доказательство:** `test_totals_follow_quote_mode_and_are_numbers`.

### 3.2. Режим НДС карточка брала из `.env`, а не из расчёта клиента

**Было:** у клиента включены «цены с НДС» (настройка в админке), расчёт считает
НДС внутри цены, а карточка показывает ветку «Без НДС / НДС сверху» — цифры
сходятся, но смысл другой, и он расходится с письмом и КП.
**Причина:** шаблон смотрел на `prices_include_vat` из `page()` — глобальную
настройку сервера, а не на снимок КП.
**Стало:** карточка берёт режим из снимка КП (`quote.prices_include_vat`) и
показывает ровно те строки итогов, что уходят клиенту, включая разбивку НДС по
ставкам 22/10/7/5/0.
**Доказательство:** тот же тест + живой прогон.

### 3.3. КП нельзя было отправить заказу из кабинета

**Было:** в поле «Кому» стоит `ООО «Гарант-Строй» <snab@…>`, браузер считает
это неверным адресом и не даёт нажать «Отправить». Заказы из личного кабинета
клиента приходят именно так (`sender = "Компания <почта>"`), то есть дефект
бил по штатному сценарию.
**Причина:** `type="email"` + `rfq.sender` без разбора адреса.
**Стало:** `sender_address()` (parseaddr) даёт чистый адрес для формы; сервер
проверяет его тем же правилом. Если адреса в отправителе нет — поле пустое,
менеджер вводит его сам.
**Доказательство:** `test_send_form_uses_bare_address`.

### 3.4. `Infinity` / `NaN` / `1e999` в количестве роняли запрос в 500

**Было:** `Decimal("Infinity")` проходит проверку «больше нуля», падает на
округлении до 0.001 — необработанное исключение, HTTP 500.
**Стало:** количество принимается только конечным и положительным, отдельно
проверяется верхний предел `KPBOT_MAX_QTY`; ошибка — сообщением в карточке.
**Доказательство:** `test_absurd_quantity_is_rejected_with_message`.

### 3.5. Одобрение отклонённой заявки оставляло ложный след

**Было:** нажатие «Одобрить» у отклонённой заявки писало в журнал `approved` и
создавало `reply_eml`, но статус не менялся (переход запрещён). В журнале
оставалось «одобрено» без одобрения.
**Причина:** побочные эффекты выполнялись до проверки допустимости перехода.
**Стало:** переход проверяется первым; при запрете — ни журнала, ни файла.
**Доказательство:** `test_approve_of_rejected_has_no_side_effects`.

### 3.6. Подтверждение строки без количества

**Было:** строка получала статус «в прайсе», но в расчёт не входила (цена
считается только при количестве) — менеджер видел «учтено», а в КП строки нет.
**Стало:** подтвердить строку без количества нельзя, сервер просит его указать.
**Доказательство:** `test_confirm_requires_quantity`.

### 3.7. Поле «артикул или название» принимало только артикул

**Было:** набранное название отклонялось («такой позиции нет в прайс-листе»),
хотя подсказка это название находила.
**Стало:** принимается артикул или **точное** название (однозначное
совпадение). Нечёткий поиск по названию сознательно не включён: цена считается
по прайсу, и «похожая» позиция — это не та позиция.
**Доказательство:** `test_line_can_be_replaced_by_name`.

### 3.8. Отправленная заявка показывала формы правки и кнопку одобрения

**Было:** все поля и кнопки активны, но любое действие возвращало отказ
(«отправленную заявку менять нельзя»).
**Стало:** для `sent` карточка — только чтение: строки без полей, вместо
кнопок — пояснение; остаются документы, Excel и повторная отправка.
**Доказательство:** `test_sent_request_is_read_only`.

### 3.9. Форма отправки до одобрения

**Было:** форма «Отправить КП» видна всегда при настроенном SMTP, но отправка
без одобрения отклонялась — тупиковая кнопка.
**Стало:** форма появляется после одобрения; до него — подсказка «Сначала
одобрите КП». Текст письма по-прежнему можно прочитать до одобрения.
**Доказательство:** `test_send_form_is_hidden_until_approved`.

### 3.10. «Отправка не настроена» при настроенной отправке

**Было:** в блоке «Действия» всегда печаталось «Отправка не настроена: текст
ответа сохраняется в черновик…», даже когда SMTP включён и форма отправки
наверху работает.
**Стало:** текст убран; состояние SMTP описывает только блок «Отправить
клиенту» и только по факту.

### 3.11. Дата письма показывалась как RFC-строка

**Было:** `Fri, 20 Nov 2026 10:00:00` (обрезка 25 символов).
**Стало:** `20.11.2026 10:00` — `dt_ru` понимает и RFC 2822, и ISO.
**Доказательство:** `test_letter_date_is_human_readable`.

### 3.12. Пустой расчёт объяснялся числом «0»

**Было:** «В расчёт вошли не все строки: 0 требуют уточнения» — при том, что
строк нет вовсе (все удалены или исключены).
**Стало:** отдельное сообщение «В расчёте нет ни одной позиции… одобрить пустое
КП нельзя», а предупреждение о неполном расчёте — только когда есть что
уточнять.
**Доказательство:** `test_empty_quote_is_explained`.

### 3.13. Статус «КП передано в отправку» после фактической отправки

**Было:** статус `sent` ставится только после успешного `SMTP`, но подпись
говорила «передано в отправку» — менеджер не понимал, ушло письмо или нет.
**Стало:** «КП отправлено» в карточке и в очереди.
**Доказательство:** `test_sent_request_is_read_only`.

### 3.14. «Взять себе» при входе общим паролем

**Было:** кнопка показывалась, а сервер отвечал «не выбран исполнитель»:
у общей сессии нет личности, назначить некому.
**Стало:** кнопка только у вошедшего пользователя; сервер объясняет причину.
**Доказательство:** живой прогон; поведение ролей — `test_users`, `test_tenant_keys`.

### 3.15. Подстановка заголовка в адрес получателя

**Было:** адрес с переводом строки (`victim@…\r\nBcc: …`) доходил до сборки
письма и падал `ValueError` — HTTP 500; в худшем случае это скрытая копия.
**Стало:** адрес проверяется регулярным выражением до сборки письма, а
`ValueError` от заголовков перехватывается и превращается в понятный отказ.
**Доказательство:** `test_header_injection_in_recipient_is_rejected`.

### 3.16. Повторная отправка уже отправленного КП откатывала статус

**Было:** если повторная отправка падала, статус `sent` принудительно
становился `approved` — заявка снова «редактируемая», хотя клиент письмо уже
получил.
**Стало:** `sent` не откатывается; сбой фиксируется в журнале и в очереди.

### 3.17. Добавление строки не проверяло лимит

**Было:** `KPBOT_MAX_RFQ_LINES=200` действовал только при разборе письма;
добавлением вручную можно было выйти за предел.
**Стало:** проверка перед добавлением.

### 3.18. Проверка после деплоя не могла войти на защищённой установке

**Было:** `scripts/smoke.py` входил только общим паролем, а он по умолчанию
выключен и запрещён в проде — проверка «вход в интерфейс» падала на любой
правильно настроенной установке (и её привыкали игнорировать).
**Стало:** вход по почте и паролю (`--email`, по умолчанию `admin@local`),
с откатом на общий пароль для старых демо-стендов. Живой прогон: 8 из 8.

### 3.19. Вёрстка на десктопе: таблица сжималась до ширины буквы

**Было:** на экране 1533 px карточка делила 1160 px на письмо и таблицу из 9
колонок; таблице оставалось ~720 px, колонки сжимались, а глобальное правило
`td, th { overflow-wrap: anywhere }` (добавленное как мобильное исправление)
ломало слова по одной букве: «К А К   Н А П И С А Н О   В   П И С Ь М Е».
**Причина:** две колонки на ширине, которой не хватает для 9 колонок, плюс
правило переноса, попавшее в общий CSS вместо мобильного медиа-запроса.
**Стало:** на ширине от 769 px блоки идут в одну колонку, таблица получает всю
ширину, у колонок заданы размеры, длинные слова переносятся только при
необходимости, форма строки складывается в две аккуратные строки. Мобильные
правила (≤ 768 px) не изменены.
**Доказательство:** скриншоты живым Chrome на сервере (1280 и 1533 px),
снятые с реальной разметки карточки.

### 3.20. Ставка 20% из старого прайса могла попасть в документ

**Было:** настройка клиента и импорт прайса 20% уже отбивали, но строка прайса,
сохранённая до 2026 года с `vat_rate=0.20`, читалась как есть и давала счёт с
20%. Прямой вызов расчёта с 20% тоже проходил.
**Стало:** три уровня защиты:

1. `price_quote` принимает только законные ставки `{22, 10, 7, 5, 0}` —
   и для клиента, и для строки (20% и 18% — `ValidationError`);
2. чтение прайса из базы обезвреживает старую ставку: пишет предупреждение и
   берёт ставку клиента;
3. `LEGAL_VAT_RATES` переехали в домен: это правило расчёта, а не настройка.

Презентация (`scripts/build_deck.py` и сам `kpbot-deck.pptx`) тоже показывала
«НДС 20%» — пересчитана на 22% (58 660,00 + 12 905,20 = 71 565,20 ₽).
**Доказательство:** `tests/test_vat_law.py` (6 тестов).

### 3.21. «Подтвердить» терял исправленное количество

**Было:** кнопка стоит в той же форме, что артикул и количество. Человек менял
количество, нажимал «Подтвердить» — строка подтверждалась со старым числом.
**Стало:** подтверждение применяет количество из формы, потом ставит статус.

### 3.22. Количество в форме показывалось как «20.000»

**Было:** в поле количества — `20.000` из базы (3 знака после точки).
**Стало:** `20` и `2,5` — тот же формат, что в таблицах, и он же разбирается
обратно.

### 3.23. Журнал показывал ISO-время, текст ответа дублировался

**Было:** в журнале `2026-11-28T10:43:34.624514+00:00`; текст ответа выводился
дважды — в блоке «Отправить клиенту» и в «Черновике ответа».
**Стало:** `28.11.2026 10:43`; текст ответа — в одном месте.

## 4. Что работает и проверено (положительные результаты)

- **CSRF** на всех изменяющих действиях карточки: правка, одобрение, отказ,
  отправка, назначение, удаление. Проверено живьём: POST без токена → 403.
- **Изоляция**: менеджер не открывает и не одобряет чужую заявку (403);
  документы и Excel проверяют принадлежность заявки, а не имя файла; id
  валидируется (32 hex) — обход каталога невозможен.
- **Машина состояний**: повторное одобрение запрещено, `sent` — терминальный,
  правка снимает одобрение и требует подтвердить заново.
- **Деньги**: построчный НДС, ставки 22/10/7/5/0, доставка, `HALF_UP`;
  карточка, письмо, КП, DOCX, Excel и счёт берут один снимок расчёта.
- **Документы**: HTML и DOCX собираются всегда, PDF — если в окружении есть
  рабочий браузер (в этой песочнице headless Edge заблокирован, поэтому PDF нет;
  на сервере он включён — это ограничение окружения, а не кода).
- **Журнал**: каждое действие с личностью (`user:…`), причина отказа
  сохраняется.

## 5. Что осталось — это решения, а не баги

1. **Ставка НДС по строке не видна в карточке.** При смешанных 22/10 менеджер
   видит только итог и разбивку в сумме. Добавлять колонку «НДС» стоит, если
   клиенты реально выставляют смешанные счёта; это расширение, а не исправление.
2. **Номер КП не показан в карточке.** В КП и письме он есть; менеджеру удобно
   видеть «КП № 12» рядом с заявкой — но это новая строка интерфейса.
3. **`approve` не требует «все строки разобраны»**, только непустой расчёт:
   предупреждение есть, решение за человеком. Менять правило без владельца
   продукта нельзя — часть заявок сознательно отправляют с уточнением.
4. **Загрузка прайса** проверяет колонку «Цена с НДС» по глобальной настройке
   `.env`, а не по настройке клиента. Для одного поставщика это безразлично;
   при мультитенантности настройки надо согласовать — отдельная задача.
5. **История отправок** разбирает адрес из текста журнала. Работает, но
   структурное поле `to_addr` было бы надёжнее — менять схему ради косметики
   не стал.
6. **Нет подтверждения на «Отклонить»/«Удалить строку».** Для отказа есть
   причина в журнале, для удаления — пересчёт; диалог подтверждения — вопрос
   UX, а не логики.

## 6. Как воспроизвести

```powershell
cd C:\WORK\777

# все тесты (542)
python -m unittest discover -s tests

# только регрессии карточки
python -m unittest discover -s tests -p "test_rfq_page.py" -v

# живой прогон: сервер на отдельной копии данных
$env:KPBOT_DATA_DIR="$PWD\.tmp\live\data"
python -m kpbot.cli serve --port 8010
python scripts/smoke.py --url http://127.0.0.1:8010
```

Регрессионные тесты: `tests/test_rfq_page.py`, `tests/test_vat_law.py`.
