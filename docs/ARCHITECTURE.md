# Архитектура и принятые решения

Документ фиксирует **почему** сделано так, а не иначе. Ссылки на стандарты:
[OWASP ASVS 5.0.0](https://asvs.owasp.org/) (опубликован 30.05.2025),
[OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/), OWASP Cheat Sheet Series.

## 1. Границы

**Входит:** приём письма, извлечение позиций, матчинг с прайсом, расчёт, КП, черновик ответа, одобрение человеком.

**Не входит:** 1С, WhatsApp, мультитенантность, биллинг, регистрация, мобильное приложение, микросервисы, Kubernetes.
Всё это появляется после третьего платного клиента, не раньше.

## 2. Форма системы: модульный монолит

Один разработчик, один сервер, бюджет порядка 5 тыс. ₽/мес. Микросервисы на этом этапе дают
распределённые транзакции и сетевые отказы — то есть только новые способы сломаться.
Границы модулей держатся портами (`LineExtractor`, адаптеры рендера), поэтому вынести
сервис позже — работа на день.

```
api (FastAPI) ── pipeline (use case) ──┬── domain      (сущности, деньги, расчёт; без I/O)
                                       ├── matching    (нормализация, скоринг)
                                       ├── extract     (правила; LLM — за протоколом)
                                       ├── pricelist   (XLSX/CSV)
                                       ├── mailparse   (.eml, сборка ответа)
                                       ├── render      (Jinja2/HTML, DOCX, браузер→PDF)
                                       └── store       (SQLite; в проде Postgres)
```

## 3. Модель данных

`price_items` (sku PK, name, unit, price TEXT, currency) — цена хранится **строкой из Decimal**,
не float. `rfqs` (id, message_id UNIQUE, sender, subject, received_at, status, raw_text).
`rfq_lines` (rfq_id, idx, raw_text, qty, unit, matched_sku, score, status, note).
`quotes` + `quote_lines` (снимок расчёта: КП не «пересчитывается» задним числом).
`artifacts` (kind: kp_html / kp_docx / kp_pdf / reply_eml, path, sha256).
`decisions` — журнал: кто, что, когда, почему.

## 4. Состояния

`received → parsed → priced → draft_ready → approved → sent`, терминальные `human_review`, `rejected`.
Переход в `sent` возможен только из `approved` и только действием человека или API-ключа.

## 5. Ключевые решения

| Решение | Почему | Что отвергли |
|---|---|---|
| **LLM не назначает цену** | цена — юридическое обязательство; модель извлекает, код считает по прайсу | «пусть модель посчитает» |
| **Человек в контуре** | отправка клиенту без проверки = репутационный риск | автоотправка |
| **Decimal + ROUND_HALF_UP** | float даёт копеечные расхождения в длинных таблицах | float, «потом округлим» |
| **Идемпотентность по `message_id`** | повторный поллинг почты не должен создавать дубли | «проверим на глаз» |
| **Сомнительное — человеку** | неверная цена хуже отсутствия КП | «угадаем по максимуму score» |
| **HTML + DOCX как основные форматы** | работают всегда; PDF — необязательный адаптер | «только PDF» |
| **SQLite в прототипе** | ноль инфраструктуры; контракт store не меняется при переходе на Postgres | сразу тащить Postgres+Redis |
| **Правиловый экстрактор** | детерминизм и отсутствие утечки ПДн в LLM | сразу LLM |

## 6. Безопасность: что закрыто и где смотреть

| Риск | Мера | Файл |
|---|---|---|
| SQL-инъекции | только параметризованные запросы `?`, без f-string | `store.py` |
| Валидация входа | Pydantic, `extra="forbid"`, лимиты размеров | `web.py` |
| XSS | autoescape Jinja2, никакого `\|safe` | `render.py`, шаблоны |
| CSRF | HMAC-токен от сессии в каждой форме | `security.py`, `web.py` |
| Подбор пароля | rate limit на вход, constant-time сравнение | `security.py` |
| Утечка через API | ключ в заголовке, 401 без деталей | `web.py` |
| DoS по размеру | `Content-Length` проверяется до чтения тела; лимит файла | `web.py` |
| Кликджекинг / MIME-sniffing | CSP, `X-Frame-Options: DENY`, `nosniff` | `web.py` |
| Path traversal | имена файлов не используются, ID — uuid4 | `pipeline.py` |
| SSRF | ссылки из письма не открываются вообще | `mailparse.py` |
| ПДн | письма не логируются целиком; LLM выключен | `pipeline.py` |
| Prompt injection (на будущее) | письмо = данные, не инструкции; JSON-схема + валидация ответа | `extract.py` (протокол) |

Чего **нет** и что нужно до продакшена: argon2id для паролей, серверные сессии в Redis,
шифрование токенов почты at rest, аудит доступа к ПДн, уведомление РКН, договор поручения
обработки, пентест перед энтерпрайз-продажей.

## 7. Наблюдаемость

Сейчас: структурные логи (stdout), журнал решений в БД, `/api/v1/stats`, health.
Дальше: Prometheus-метрики (`emails_in`, `parse_fail_rate`, `match_rate`, `time_to_draft`,
`quotes_sent`, `pdf_skipped`), алерты на рост `pdf_skipped` и `human_review`.

## 8. Тесты

Уровни: unit (домен без I/O) → интеграционные (пайплайн на временной БД) → API (TestClient:
ключ, CSRF, лимиты, заголовки). 44 теста, запуск `python -m unittest discover -s tests`.
В проде добавить: property-based (Hypothesis) на суммы, fuzz на парсер цен, golden-файлы PDF,
`bandit` + `pip-audit` + `gitleaks` в CI.

## 9. Дорожная карта (12 недель)

| Фаза | Недели | Результат | Готово, когда |
|---|---|---|---|
| 0. Проверка | 2–3 дня | 5 интервью, baseline «минуты на КП» | есть клиент и цифра «до» |
| 1. Каркас | 1–2 | прайс, матчинг, расчёт, КП | 100 позиций матчатся, тесты зелёные |
| 2. Почта | 3–4 | IMAP, очередь, outbox, UI | сквозной сценарий на реальном письме |
| 3. Пилот | 5–6 | работа у клиента в тень-режиме | менеджер отправил КП из черновика |
| 4. Крепость | 7–8 | лимиты, роли, бэкапы, метрики, red-team промптов | чек-лист ASVS L2 по ключевым пунктам |
| 5. Тираж | 9–12 | шаблон под вертикаль, второй клиент | второй клиент без нового кода |

**Метрики успеха пилота:** доля строк с ручной правкой < 10%, «не найдено» < 15%,
время «письмо → черновик» < 5 минут, ноль отправок без подтверждения.

## 10. Риски

1. Точность извлечения на грязных письмах — лечится правилами и ручной правкой, не «умной моделью».
2. Матчинг нестандартных названий — метрика «доля не найдено», порог настраивается.
3. Кастомизация под клиента съедает маржу — отсюда требование: третий проект в той же вертикали
   должен быть копией первых двух.
4. Зависимость от почтового провайдера клиента (лимиты IMAP, OAuth) — резервный путь: пересылка
   писем на адрес сервиса.
