## 7. Что изменилось в поведении (важно при обновлении)

1. **Ставка НДС по умолчанию 22%.** Если у клиента 10/7/5/0% — задайте
   `KPBOT_VAT_RATE` явно. Старые КП не пересчитываются (снимок), новые — по новой ставке.
2. **Номер КП** теперь сквозной (`quotes.number`), миграция добавит колонку сама.
   Нумерация начинается с 1 в каждой базе клиента.
3. **Разбор количества стал строже:** «10 000» = 10000, количество после тире
   приоритетнее, «0 шт» не создаёт позицию.
4. **Матчинг строже:** позиция без размера при наличии конкурирующих вариантов и
   позиция с равными оценками уходят человеку. На демо-письмах результат тот же
   (2 из 3 готовы к отправке), но угадывание размера прекратилось.
5. **Ключ обучения изменился** (сохраняются размеры). Старые выученные пары
   перестанут применяться — это безопасное направление: больше ручной проверки.
6. **В проде** вход общим паролем выключен: нужен пользователь (`admin@local`
   создаётся из `KPBOT_UI_PASSWORD` при первом запуске).
7. **HTTP-сервис 1С** без `X-Kpbot-Token` отвечает 401 — обновите `ОжидаемыйТокен()`
   и `KPBOT_ONE_C_SERVICE_TOKEN` одновременно.

## 8. Что осталось (честный список)

### P0 — до показа клиенту

1. **НДС по строкам (смешанные ставки).** Сейчас одна ставка на КП: у оптовика
   с товарами 20% и 10% документ будет неверным. Нужно поле ставки у позиции
   прайса и в `QuoteLine`, сумма НДС по строкам, лист «Для 1С» по строкам.
2. **Вложения писем не разбираются** (`mailparse.py`: «вложения пока не разбираем»).
   Excel/PDF-заявка → `NotAnRfq`. Для реального снабженца это половина писем.
3. **Один API-ключ на все клиенты** + `X-Tenant`: ключ клиента A читает данные
   любого клиента, чей код узнает. Нужны ключи, привязанные к клиенту.
4. **Один процесс uvicorn и SQLite**: лимиты и кэш в памяти, один писатель.
   Для 1–3 клиентов приемлемо, для роста — Postgres + Redis.

### P1 — после первого пилота

5. **Кабинет:** DDL при каждом запросе (`cabinet_store.init_schema`), создание
   заказа не в одной транзакции с RFQ (возможен 500 и осиротевшая заявка).
6. **1С:** нет повторов/идемпотентности при сетевом сбое; ошибки 1С показываются
   в интерфейсе как есть.
7. **OAuth:** `state` генерируется, но не проверяется; токен лежит в открытом JSON.
8. **Наблюдаемость:** нет метрик (Prometheus), только логи и `/api/v1/stats`.
9. **E2E-браузер и golden-файлы DOCX/PDF:** вёрстка и документы проверяются
   глазами; поэтому баги вида «Fri, 20 No» и жили.
10. **Презентация** (`presentation/`) пересчитана на 20% и старые числа —
    пересобрать после смены ставки.

### P2 — технический долг

11. `web.py` — 56 маршрутов в одном файле, проверки доступа копируются.
12. Дублирование: два скорера (`similarity`/`_score`), два сборщика ответа,
    три пути расчёта денег.
13. Тесты матчинга частично проверяют `similarity()`, который в проде не используется.
14. Пустой `.tmp/` с артефактами прошлых прогонов (190 КБ логов) — чистить.

### Вне кода (блокеры продажи, без изменений)

15. Сервер в Польше — нарушение ч. 5 ст. 18 152-ФЗ; нужен переезд в РФ.
16. Документы по ПДн не заполнены и не подписаны.
17. Лицензия 1С: учебная не годится для эксплуатации (нужна ПРОФ/КОРП).
18. **Пароль сервера и доступы были переданы в чате** — сменить пароль root
    и ключи после деплоя.
19. **Ключ LLM (`sk-aitunnel-…`) тоже был в чате** — после проверки его стоит
    перевыпустить в кабинете AITunnel и обновить `KPBOT_LLM_API_KEY` в `.env`
    на сервере.

бэкап → `git pull` → `.venv`/зависимости → правка `.env` (НДС 22%, общий пароль
выключен) → `systemctl restart` → проверка `healthz` с откатом на предыдущий коммит.

После появления доступа деплой — это:

```bash
ssh root@45.152.202.114
git -C /opt/kpbot pull --ff-only
# .env: KPBOT_VAT_RATE=0.22, KPBOT_ALLOW_SHARED_LOGIN=false
systemctl restart kpbot && systemctl status kpbot --no-pager
curl -s http://127.0.0.1:8000/healthz
```
